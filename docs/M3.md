# M3: game startup and Direct3D 9 initialization

## 1. Scope

M3 covers execution of the original CD 1.1 game code from WinMain through
window creation, dynamic DLL loading, the startup DirectShow probe and
Direct3D 9 device initialization. The host records the calls and results
needed to reproduce this boundary.

The results in this document are from the Linux x86-64 host, using
DXVK Native 3.1.1 with lavapipe under Xvfb for the rendered run. They do
not establish Android runtime compatibility; Android uses a separate
DXVK Native fork. The full-game Android APK has since been run on a Galaxy
S24 Ultra and reached the animated intro rendering loop, but has not yet
reached the main menu.

## 2. Startup path

The measured startup path performs the following operations:

1. Enters the game's WinMain after CRT initialization.
2. Reads configuration and registry values.
3. Creates the main game window.
4. Loads the DLLs required by startup.
5. Runs the Windows Media / DirectShow startup check.
6. Loads the D3D9 host module and calls Direct3DCreate9.
7. Queries the adapter and display configuration.
8. Creates the game's Direct3D 9 device and uses its resources.

The DirectShow startup objects satisfy only the probe contract. They do not
implement ASF playback, the game's texture renderer or film export; see
[DIRECTSHOW-STARTUP.md](DIRECTSHOW-STARTUP.md).

## 3. Direct3D 9 device request

The game requests a full-screen 1024×768 HAL device with:

- X1R5G5B5 backbuffer format;
- D16 automatic depth-stencil surface;
- hardware vertex processing;
- one backbuffer;
- discard swap effect;
- multithreaded device creation.

The game does not query all device capabilities before this request.
The complete format, resource and method trace is documented in
[D3D9-REQUIREMENTS.md](D3D9-REQUIREMENTS.md).

## 4. Backend integration

The Linux host uses DXVK Native 3.1.1 through the guest D3D9 bridge.

The bridge keeps guest COM objects and vtables in guest memory. Host-side
DXVK objects are stored in adapter tables keyed by guest object address.
Guest-visible pointers and structures are converted at the boundary; host
pointers are not written into guest memory.

The backend forwards the game's device creation, resource operations and
rendering calls. Methods without an implementation stop with a diagnostic
rather than returning fabricated success.

See [DXVK-INTEGRATION.md](DXVK-INTEGRATION.md) for the host ABI and
backend details.

## 5. Verified Linux results

With the DXVK backend enabled, the game's own D3D9 CreateDevice succeeds.
The game then executes its intro and main-menu rendering code. The main
menu responds to mouse input, and starting a new game reaches the 3D studio
lot.

The rendered output is produced by the game's own code through DXVK Native.
The menu video backdrop is absent because DirectShow media playback is not
implemented.

The headless M3 regression scenario remains available. It stops at the
game's CreateDevice boundary and records the requested parameters.

## 6. Test commands

Run the host with DXVK Native:

    cd /path/to/game
    /path/to/build/tm_host . --d3d9 dxvk

Run the headless boundary regression:

    python3 tests/m3_boundary.py --host build/tm_host --game /path/to/game

Run the unit tests:

    ctest --test-dir build --output-on-failure

The M3 boundary baseline is stored in tests/baselines/. It must be updated
only when the changed runtime behavior has been reviewed and the baseline
change is intentional.

## 7. Subsystems outside this test boundary

- DirectShow media playback and film export;
- full audio output and codec support;
- Android touch input and Activity lifecycle. The game currently presents
  animated intro frames on the Galaxy S24 Ultra but remains on the splash;
  the Android finger-to-Win32 mouse bridge is still being validated;
- Android guest-memory reservation and PE mapping;
- full studio-session stability, save/load and long-duration testing.

The Android app target and its validation state are documented in
[ANDROID-PORT-AUDIT.md](ANDROID-PORT-AUDIT.md).
