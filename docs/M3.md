# M3: from WinMain to an initialised graphics device

Goal: run the original code from `WinMain` until the game has created its
main window and its Direct3D 9 device with the parameters it chooses, and
has created, used and released its resources, with every call recorded.
Rendering calls the game reaches on the way (`Clear`, `BeginScene`,
`EndScene`, `Draw*`, `Present`) are traced. A rendered frame is M4.

Starting point (docs/M2.md): `WinMain` runs about 300 ms, shows the game's
first-launch notice, and stops at `GetDiskFreeSpaceExW` (since passed, step 2).

Current state: with `--d3d9 dxvk` the game's own `CreateDevice` succeeds on
DXVK Native, and the game runs its intro and main menu, drawing them itself
(steps 5–6, [DXVK-INTEGRATION.md](DXVK-INTEGRATION.md) 5). Without the
option the run is headless and stops at `CreateDevice`, with every
parameter recorded; `tests/m3_boundary.py` holds that boundary.

## Scope

- the start-up path from `WinMain` to the device: files, registry, the
  window, the DLLs the game loads at run time;
- the game's adapter, mode, format and caps queries, and its own
  `CreateDevice` call;
- the resources the game creates, uses (`Lock`/`Unlock`, `Set*`) and
  releases;
- tracing the rendering calls the game reaches, with their `HRESULT`s,
  including `Present` and lost devices;
- window messages, timers, threads and waits around the device.

Planned artefacts: a JSON and text log of every D3D9 call; a
`CreateDevice` regression test (`tests/m3_createdevice.py`) with its saved
trace; `docs/D3D9-REQUIREMENTS.md` (interfaces, shader models, formats,
pools and caps the game uses), from which the D3D9 backend is chosen
(docs/AUDIT.md 5.3).

## Work in detail

### 3.1 Clear the start-up path

Iterate: run, read the first stub or fault, implement it, run again. Each
wall gets an entry in `docs/bringup.md` with the log line and the fix, as in
the reference project.

`GetDiskFreeSpaceExW` is done (step 2), and so is the DirectShow start-up
probe ([DIRECTSHOW-STARTUP.md](DIRECTSHOW-STARTUP.md) 9). `Direct3DCreate9`
and the device-free `IDirect3D9` queries are done (3.4). Known next: a
device for `CreateDevice`. The wide-string file
family (`CreateFileW`, `FindFirstFileW`, `GetFileAttributesW`,
`CreateDirectoryW`, ...: 15 stubs) has not been called so far. If it is
reached, it goes in one module, implemented by converting to UTF-8 and
calling the ANSI paths, so the wide and narrow calls share one path
translation.

Also expected on this path, from the import table: `RegOpenKeyExW` /
`RegQueryValueExW` (settings), `GetVersionExW`, `CoInitializeEx`,
`GetSystemPowerStatus`, the keyboard-layout calls.

### 3.2 Registry and configuration

Record every registry key the game opens. Seed an in-memory registry
(win32hle `advapi32.c`) with what the Russian installer would have written,
from the MSI's Registry table (`Software\Lionhead Studios Ltd`), plus
whatever the run shows the game reads. The first-launch notice suggests the
game keeps a "has run before" flag somewhere: find out where, so later runs
are not always first runs.

### 3.3 The window

win32hle's `user32` creates windows without a display. Check that the
game's window class, styles and `AdjustWindowRect` sizes come through, that
`ShowWindow`, `SetCursor`, `ClipCursor`, `GetClientRect` and
`ClientToScreen` answer sensibly, and that `WM_ACTIVATE`/`WM_SETFOCUS`
arrive: games often wait for focus before starting the renderer.

### 3.4 A recording Direct3D 9 layer

`tm_d3d9.c`: `Direct3DCreate9` returns a guest-visible COM object whose
vtable slots are shim VAs. Every interface the game touches is listed in
full (IDirect3D9, IDirect3DDevice9, surfaces, textures, vertex and index
buffers, shaders, state blocks, queries), and every method logs its call and
arguments.

- Objects and their vtables live in guest memory (`hle_alloc`), never host
  pointers (B8).
- `GetAdapterIdentifier`, `GetDeviceCaps`, `EnumAdapterModes`,
  `CheckDeviceFormat` answer from a documented capability profile that describes what the backend really does.
- Resource creation allocates real guest memory, so `Lock`/`Unlock` give the
  game buffers it can fill.
- `Present` counts calls, returns the `HRESULT` the device state calls for
  and pumps the host's message queue; it does not need to show anything
  in M3.

This layer is the measurement M3 needs to choose between DXVK-native and an
own D3D9 implementation (docs/AUDIT.md 5.3). The choice is DXVK Native: it
is measured, and its integration decisions are in
[DXVK-INTEGRATION.md](DXVK-INTEGRATION.md) 4.

### 3.5 What else LoadLibrary asks for

The game loads `dinput8.dll`, `dsound.dll` or `OpenAL32.dll`, `WMVCore.dll`
and others at run time. For each one reached in M3: record what is asked,
then either answer with a minimal implementation (a device that
exists and reports no input; audio that accepts buffers and plays nothing)
or report "not available" if the game copes with that. Which one was chosen
is recorded per DLL. Intro videos (DirectShow) are expected to be skipped
or to fail here; making them play is M5. Found since: the start-up check
itself creates DirectShow objects (a filter graph, a capture graph builder
and the Windows Media ASF Writer filter) and stops the game if it can't.
So some of DirectShow is needed before the main window
(IMPORTS.md, "The current boundary").

### 3.6 Exceptions (B4)

Measured ([EXCEPTIONS.md](EXCEPTIONS.md)): 5,646 functions with C++ EH
frames and 1,031 that throw; the start-up run enters 186 of the former and
none of the throws is taken. No `RaiseException` call. If the game throws on
its normal path, re-lift with pcrecomp's EH pass (landing pads per lifted
frame) and port its `eh32.c` dispatcher to win32hle; it is Windows-only
today in its TLS and headers, not in its logic.

### 3.7 Threads

The game starts worker threads (the reference saw them before the first
frame). win32hle runs them under one machine lock. Record each
`CreateThread` start address, and watch for spin-waits that never yield.

### 3.8 Tooling

- `--report FILE`: imports called (with counts), D3D9 methods, threads,
  registry keys, files opened: the M3 measurements in one JSON file.
- `--calltrace`/`--firsthit` in `tm_trace.c` (now a stub), for the walls that
  are not a stub but wrong behaviour.
- `tests/m2_winmain.py` (exists) and `tests/m3_createdevice.py` (once `CreateDevice` succeeds).

## Carried over from M2

Linux arm64 and the Android `adb shell` run of the M2 binary are still open.
They do not block M3, which runs on x86-64, but they should be done before
M4 so the ARM64 build and its speed are known early (B9, B10). They need an
arm64 machine or emulator and the Android NDK.

## Out of scope for M3

A rendered frame and correct visual output (M4), a complete rendering backend, video, audio output and input (M5),
the Android app (M7).
