# M2: the lifted start-up code reaches WinMain

Date: 2026-11-24. Host: Linux x86-64 (Ubuntu 24.04, clang 18), 4 cores,
16 GB. Game: `Movies.exe` 1.1, Russian CD.

This is a Linux x86-64 execution report. Import/stub counts in this file
refer to the measured M2 run; current implementation status is maintained in
[IMPORTS.md](IMPORTS.md).

**Result:** on Linux x86-64 the recompiled CRT start-up of the real CD
executable runs from the PE entry point through every C and C++ initializer
into `WinMain`, and `WinMain` then runs the game's own start-up for about
300 ms. That is all it shows. Nothing is drawn, no window exists yet, and the
game does not run.

M2 also names Linux arm64 and an Android device (`adb shell`) as targets.
Neither has been run yet; both remain open (section 9).

the host's current directory, mapped through the drives:

and `Z:\<host path>` anywhere else. The CRT start-up code before WinMain
handles that string differently by length, and outside drive C: it also calls
`FindFirstFileA`. Measured, with the same binary and a fresh user directory:

|---|---|---|---|

| `/tmp` | `Z:\tmp` | 12,994 | 1,246 |

| `/home/user/the-movies-android` | `Z:\home\user\the-movies-android` | 13,025 | 1,246 |

The host environment variables do not change the count (the same numbers under
`env -i`), and neither does whether `D:\My Documents` exists. An earlier
version of this report put the difference down to My Documents; that was
wrong, the two runs it compared had different working directories. The
regression test runs the game from its install directory, as a Windows
shortcut does (12,978 entries).

Regression test: `tests/m2_winmain.py`.

The `GetProcAddress ... not answered` lines are expected. The CRT probes
for Windows XP+ APIs (fiber-local storage) and falls back to TLS when they
are missing, as it would on Windows 2000.

## 3. Why this is WinMain and not a stub

- The marker is printed by the `RECOMP_ENTER` hook, the first statement of
  the lifted body `sub_005303C0` (`gen/recomp_0017.c`, line 21,327:
  `RECOMP_ENTER(0x005303C0u)`). It fires only when the lifted function itself
  is entered, by the CRT's `call 0x5303c0` at `0x00A316F0`.
- `0x005303C0` was identified as WinMain from the CRT code, not from the
  lift: `WinMainCRTStartup` calls it with `GetModuleHandleA(NULL)`, 0, the
  command line and the `STARTUPINFO` show flag (docs/AUDIT.md).
- **Without** `--stop-at-winmain` the game keeps going: 2,618,608 lifted
  function entries and 1,387 distinct functions in about 300 ms. Then
  `WinMain` itself (`in lifted sub_005303C0`) shows the game's own
  first-launch notice through `MessageBoxW`: a Russian text that the game
  starts with maximum graphics settings and that they can be lowered in the
  video options. The text decodes correctly from UTF-16. No stub contains
  this text; it comes from the game's string data.

## 4. Where it stops: the next wall

Run without `--stop-at-winmain`:

```
[poc] WinMain 0x005303C0 entered: 14.4 ms, 13011 function entries, 1246 distinct functions
[MessageBoxW] type 0x0 caption "The Movies(TM)."  (first-launch notice)  answered OK
[win32hle] FATAL: unimplemented import GetDiskFreeSpaceExW (0x7F002D80) called from guest 0x00992DC0

=== abort (win32hle fatal) after 307.9 ms ===
  in lifted sub_00992DC0, last import GetDiskFreeSpaceExW
  eax=1040BEF0 ebx=00000000 ecx=103FFCF4 edx=103FFCAC
  esi=0000000A edi=00000014 ebp=00000040 esp=103FFB94
  2618608 function entries, 1387 distinct functions, WinMain ENTERED
  guest stack at esp:
    00000000 1040BEF0 103FFCAC 103FFCF4
    103FFCFC 0000000A 00000014 103FFFB8
    00000000 103FFBC4 00000003 00000014
    00736559 49007844 545F5345 0000004D
```

- **Cause:** an import with no implementation. `GetDiskFreeSpaceExW` is a
  stub; win32hle stops the run when a stub is called.
- **Where:** lifted `sub_00992DC0`, called from `WinMain`'s start-up path.
- **Arguments** (stdcall, `esp` → `[ret][path][avail][total][free]`):
  path `0x1040BEF0` (a wide string in the guest heap), three out-pointers
  on the stack. The game checks free disk space, most likely for its save
  directory.
- **Not a crash:** no fault, no unresolved jump. The lifted code did exactly
  what the original would.

The registers are the guest's globals as of the last call. With
`RECOMP_LOCAL_REGS` a function body keeps local copies and writes them back
before each call, so these are the values the import was called with.


**Update, 26 November 2026 (source-level, not yet runtime-verified):**
the Android host branch now implements `GetDiskFreeSpaceExW` in
`src/host/tm_kernel32.c` and registers it through `tm_kernel32_shims`.
That removes the specific missing-import implementation gap shown in this
historical M2 log. It does not yet prove that the Android build reaches or
passes this call; the next runtime stop must be established from a new trace.

## 5. A defect found and fixed on the way: a skipped global constructor

The first full run reached WinMain too, but printed
`ICALL: unresolved VA 0x00C6CE80 from 0x00A31D2D`. `0x00C6CE80` is one of
the game's 697 C++ dynamic initializers (CRT table `__xc`,
`0x00D9E000`–`0x00D9EAE8`, slot `0x00D9EA18`). It constructs a 5-element
global array and registers its destructor. The function catalog had missed
it, so the call returned without running it: that global was never built.

Fix: `tools/crt_init_seeds.py` reads both CRT tables (`__xc`, 697
initializers; `__xi`, 5) from `_cinit` and adds every entry to the catalog's
seeds. After the re-catalog, every initializer is in the dispatch table, and
the run above has no unresolved `ICALL` or `ITAIL`.

| `0xC5ADDE2F` | `sub_00B6FD47` | outside the image |


A second pass over the private lift artifact (`functions.json` plus all 215
generated translation units) adds useful triage context:

- Six targets are outside the PE code range `[0x00401000, 0x00C72000)`.
- All seven owner functions have zero incoming **direct-call** edges in the
  function catalog. This does not rule out indirect references through
  function pointers, tables, callbacks or virtual dispatch.
- `0x0086AAC6` is inside `.text`, exactly one byte after the catalogued
  two-byte thunk `sub_0086AAC5`. Its lifted body is a short jump to that
  second byte, so the target is an overlapping instruction entry rather than
  a normal function start. It has no dispatch entry. The raw bytes and any
  indirect references still need checking before classifying it as dead code.

These observations make the six out-of-range targets look more like false
code discovery than ordinary missing functions, but they are not proof that
the paths are unreachable. Keep all seven visible as unresolved until a
runtime trace or a byte-level/catalog audit settles them.

## 9. Scope and remaining validation

M2 verifies the Linux x86-64 CRT startup path only. It does not verify:

- Linux AArch64 execution;
- the Android app's guest-memory reservation, PE mapping or import binding;
- the Android game's execution through WinMain;
- the CRT exit path and atexit destructors.

The Android application and full-game build status are maintained in
[ANDROID-PORT-AUDIT.md](ANDROID-PORT-AUDIT.md). The standalone Android D3D9
probe is a separate test and is not evidence of an Android game launch.
